# Manny 프레임 보정(팔 체인 롤 보정), 아래팔 비틀림 이동, 입력 클램프

브랜치 `feature/manny-frame-refinement`의 변경 설명입니다. 모델 재학습 없이, Manny 동작을 모델에 넣기 전의 **스켈레톤 변환 오차**를 바로잡아 전환 품질을 높였습니다. 세 가지 모두 모델 입력 직전에 적용하고 출력 직후에 되돌리므로, 내보낸 입력·역매핑·C++ 플러그인 코드는 그대로입니다. 여기에 더해 기본 목표 배치(`endpoint_velocity`)가 목표 클립의 방향을 바꾸지 않도록 고쳤습니다(3.5).

## 요약

- 전환이 어색했던 가장 큰 원인은 모델이 아니라 **Manny→LAFAN 보정 행렬의 팔 비틀림(롤) 오차**였습니다. 팔꿈치가 LAFAN에 없는 축으로 꺾여 들어가면서, 입력 z-score가 최대 45까지 튀었고 루트·다리 예측까지 망가뜨렸습니다.
- 팔 체인 4개 관절의 롤 값을 실제 Manny 동작에서 추정해 보정하고(`B' = B · Rx(roll)`), 분포 밖으로 크게 벗어나는 쇄골·팔 입력은 z ±3으로 묶었습니다.
- Idle_Walk_Jog의 `A_JogFwd_Loop`는 아래팔 뼈 자체에 약 60°의 비틀림(회내)이 들어 있어, 롤 보정 뒤에도 아래팔 입력 z가 71까지 튀고 클램프가 아래팔을 47°나 꺾었습니다. 이 비틀림을 모델 입력 전에 손으로 옮기고 출력 뒤 되돌리게 했습니다. 관절 위치와 손 방향은 바뀌지 않습니다.
- 같은 클립 안 구간을 지우고 다시 채우는 테스트에서 모델 오차가 **단순 보간 대비 0.96배 → 0.51배**로 줄었습니다. 추정에 쓰지 않은 Idle_Walk_Jog 클립에서는 **0.57배 → 0.37배**, Quinn 클립에서는 **0.97배 → 0.47배**입니다.
- Idle_Walk_Jog 전환 6개(N=20)에서 관절이 원본보다 크게 튀는 프레임 수가 **106 → 29(롤 보정·클램프) → 16(비틀림 이동 추가)**으로 줄었습니다.
- A_Idle은 몸 전체가 Walk·Jog 진행 방향에서 약 23° 돌아선 자세입니다. 기존 목표 배치는 목표 클립의 골반 방향을 시작 클립에 맞춰 돌려서, IdleToJog가 23° 대각선으로 달리고 Idle로 끝나는 전환은 Idle이 −23° 돌아간 채 끝났습니다. 이제 목표 클립은 내보낸 방향을 유지하고 회전은 모델이 생성 구간 안에서 만듭니다. 6개 전환 모두 끝 방향이 원본 클립과 0.0°로 일치합니다.

## 1. 증상과 원인

| 관찰 | 수치 |
| --- | --- |
| Run 입력 팔꿈치(ForeArm) 채널 z-score | 최대 45 (LAFAN 해당 채널 std 0.014) |
| Run 입력 쇄골(Shoulder) 채널 z-score | 최대 29 (LAFAN 쇄골은 거의 고정, std 0.012) |
| Run 클립 자기 복원 오차 (기존) | 단순 보간의 **1.25배** — 모델이 보간보다 나쁨 |
| Walk→Run(N=20) 경계 루트 보정량 (기존) | 11.5 cm — 모델 궤적이 목표와 어긋나 후처리가 루트를 끌어당김 |
| A_JogFwd_Loop 아래팔 z-score (롤 보정 후) | 왼쪽 71, 오른쪽 49 — 아래팔 뼈 축 둘레 비틀림 약 60°·21° |

z-score가 큰 입력 몇 채널이 인코더에서 프레임 토큰 전체를 오염시켜, 팔뿐 아니라 루트와 다리 예측까지 틀어졌습니다. 이 채널들만 ±3으로 잘라도 Run 복원 오차가 절반 이하로 줄어드는 것으로 확인했습니다.

팔꿈치 z는 팔을 많이 굽히는 Run·Jump에서만 크게 튀고, 팔을 편 Idle에서는 작았습니다. 이는 **보정 축이 뼈 축을 중심으로 틀어져 있을 때** 나타나는 패턴입니다. 실제로 Manny 애니메이션에서 팔꿈치가 굽는 축을 측정하니, LAFAN 힌지축(로컬 +Z)에서 24~30° 기울어 있었습니다. 무릎은 9~14° 수준이었습니다.

롤 보정과 클램프를 넣은 뒤에도 Jog 전환에서는 9→10, 29→30 접합부에서 아래팔과 손이 튀었습니다. 원인은 클립 쪽에 있었습니다. 아래팔 로컬 회전을 "팔꿈치 굽힘(+Z) × 뼈 축(+X) 둘레 비틀림"으로 나눠 보면, MM·MF·A_Idle·A_Walk 클립은 비틀림이 7° 이하인데 A_JogFwd_Loop만 왼쪽 −61°(±9°), 오른쪽 +21°(±11°)였습니다. 손을 돌리는 회내 동작이 손이 아니라 아래팔 뼈에 실린 것입니다. LAFAN의 아래팔은 순수 힌지라(해당 채널 std 0.014, 약 0.8°) 이런 입력은 학습에 없습니다. 클램프가 이를 억지로 분포 안으로 꺾으면서 모델은 실제와 47° 다른 아래팔을 보고 동작을 만들었고, 그 차이를 되돌리는 과정에서 시작 프레임에 14°/프레임의 튐이 생겼습니다(원본 Jog 클립의 아래팔 최대 가속은 4.7).

## 2. 보정 행렬이란

Manny와 LAFAN은 관절 22개를 공유하지만 뼈마다 로컬 좌표축 정의가 다릅니다. 그래서 `manny_lafan_transform.apply_global_rest_correction`이 관절마다 고정 3×3 회전 `B`를 곱해 Manny 회전을 LAFAN식 회전으로 바꿉니다. 값은 `Tools/MannyLafanMapping/rest_pose_corrections_22_prototype.json`에 있습니다.

회전의 자유도 3은 **뼈 방향(2) + 뼈 축 둘레 롤(1)**입니다. 현재 값은 Manny `MM_Idle` 0번 프레임과 LAFAN `walk2_subject4` 454번 프레임을 같은 자세로 가정해 역산했습니다. 팔을 편 자세에서는 30° 비틀려도 겉모양이 거의 같기 때문에, 포즈 한 쌍으로는 롤을 정할 수 없습니다. 롤은 관절이 **굽는 방향**으로만 드러납니다.

## 3. 변경 내용

### 3.1 롤 추정 — `Tools/MotionInference/estimate_frame_refinement.py`

1. 플러그인으로 내보낸 Manny 동작(정규화하지 않은 `model_input.json`)에서 팔꿈치 로컬 회전을 모읍니다.
2. 기준 프레임 대비 상대 회전의 회전축을 PCA로 구해, 위팔 프레임과 아래팔 프레임에서의 굽힘 축을 얻습니다.
3. 그 축의 Y 성분이 0이 되도록 각 프레임을 뼈 축(+X) 둘레로 돌리는 롤을 계산합니다.

Manny 클립 7개(MM_*)에서 추정한 결과는 `configs/manny_frame_refinement_v1.json`에 있습니다.

| 관절 | 롤 | 보정 전 굽힘 축 | 보정 후 |
| --- | --- | --- | --- |
| LeftArm (위팔) | −30.0° | (0.034, 0.500, 0.865) | (0.034, 0, 0.999) |
| LeftForeArm (아래팔) | −29.2° | (0.035, 0.488, 0.872) | (0.035, 0, 0.999) |
| RightArm | +24.2° | (−0.103, −0.408, 0.907) | (−0.103, 0, 0.995) |
| RightForeArm | +26.6° | (−0.155, −0.443, 0.883) | (−0.155, 0, 0.988) |

첫 주성분 분산 비율이 0.996~0.997이라, 팔꿈치는 거의 완벽한 단일 축 힌지입니다. 무릎(`--hinges elbows knees`)도 같은 방법으로 추정해 검증했지만 이득이 없어서 기본값에서는 뺐습니다.

### 3.2 적용 위치 — `Tools/MotionInference/infer.py`

보정 JSON 자체를 바꾸지 않고, 모델 호출 **직전에 적용하고 직후에 되돌립니다**.

```
l'_j = C_parent(j)ᵀ · l_j · C_j        # C_j = Rx(roll_j), 모델 입력 직전
l_j  = C_parent(j) · l'_j · C_jᵀ       # 모델 출력 직후
```

이는 보정 행렬을 `B' = B · C`로 바꿔 다시 내보낸 것과 수학적으로 같습니다. `FrameRefinementTests.test_refinement_equals_reexport_with_refined_calibration`이 이 동일성을 검사합니다. 이렇게 한 이유는 다음과 같습니다.

- 내보내기, 역매핑, C++ 플러그인 코드가 바뀌지 않습니다.
- 이미 내보낸 입력 파일과 데모 샘플을 그대로 쓸 수 있습니다.
- 보정 파일과 입력이 서로 다른 보정 행렬로 만들어진 경우를 해시로 검사할 수 있습니다.

### 3.3 입력 z 클램프

쇄골은 LAFAN에서 거의 움직이지 않아(6D std ≈ 0.012) 보정으로 고칠 수 없습니다. 롤 보정도 팔 프레임의 뼈 방향 기울기(5~7°)까지는 잡지 못합니다. 그래서 쇄골·위팔·아래팔·손 6D 채널의 모델 입력 z-score를 ±3으로 자릅니다.

모델은 잘린 문맥·목표를 보고 이어지는 동작을 만들지만, 결과에서는 문맥·목표를 원본으로 복원합니다. 그대로 두면 9→10, 29→30 접합부에서 그 차이만큼 관절이 튑니다. 첫 버전에서는 Run 전환의 쇄골이 한 프레임에 최대 19° 튀었습니다. 그래서 `blend_clamp_offsets`가 시작·끝의 회전 차이(원본 · 클램프본ᵀ)를 생성 구간 전체에 SLERP로 나눠 더해 원본과 이어지게 합니다. 루트 위치의 경계 보정과 같은 방식이고, 실제로 메운 각도를 `diagnostics.input_z_clamp.boundary_offset_degrees`에 남깁니다. 이 보정으로 Run 전환 접합부의 팔 최대 가속은 16~18 → 5.5~6.9 °/프레임²로 줄었고, 쇄골 회전 오차도 5.35° → 3.56°로 낮아졌습니다.

비틀림 이동(3.4)까지 넣은 상태(목표 방향 수정 전)에서 클램프를 끄면 전환 6개의 튐 프레임 수가 16 → 48(N=20)로 늘어 클램프는 여전히 필요합니다. 쇄골만 잘라도 결과는 같았습니다(16, 자기 복원 오차도 같음). Idle_Walk_Jog 전환에서 실제로 잘리는 관절은 쇄골뿐이고(경계 보정 9~13°), 팔·손 클램프는 분포 밖 입력이 들어올 때를 위한 안전장치입니다. 비틀림 이동이 없던 1차 버전에서는 팔 클램프가 핵심이었습니다(클램프 끔 183, 쇄골만 160, 8관절 29).

### 3.4 아래팔 비틀림 이동 — `twist_transfer`

롤 보정은 관절마다 **고정된** 롤입니다. A_JogFwd_Loop처럼 클립마다, 프레임마다 다른 아래팔 비틀림은 프레임별로 처리해야 합니다.

1. **측정**: 로컬 회전의 3행은 부모의 +Z(힌지축)를 관절 쪽에서 본 방향입니다. 순수 힌지 `Rz(굽힘)`이면 관절 자신의 +Z와 같고, 굽힌 뒤 뼈 축 둘레로 `Rx(a)`만큼 비틀면 관절의 Y-Z 평면에서 정확히 a만큼 돌아갑니다. 그래서 `a = atan2(l[2,1], l[2,2])`이고, 굽힘 각도와 무관합니다(`twist_angles`).
2. **이동**: 모델 입력 직전에 아래팔은 `l ← l · Rx(−a)`, 손은 `l_손 ← Rx(a) · l_손`로 바꿉니다. 아래팔 프레임만 뼈 축 둘레로 돌기 때문에 손의 방향은 그대로고, LAFAN처럼 뼈가 +X 방향이면 관절 위치도 그대로입니다. 모델은 순수 힌지 아래팔과, 회내가 손에 실린(LAFAN과 같은) 팔을 봅니다(`transfer_twist`).
3. **복원**: 문맥·목표 프레임은 측정값을 그대로 되돌립니다. 생성 프레임의 비틀림은 9번 프레임에서 문맥의 마지막 비틀림 속도로 출발해 목표 프레임에 목표의 비틀림 속도로 도착하는 3차 Hermite 곡선으로 만들어 되돌립니다. ±180°를 넘을 때는 짧은 쪽으로 돌아갑니다(`twist_curve`).

| 클립 | 아래팔 z (왼/오) 기존 → 롤 보정 → + 비틀림 이동 |
| --- | --- |
| A_JogFwd_Loop | 52.3/7.9 → 71.2/48.5 → **2.6/2.7** |
| A_WalkFwd_Loop | 8.2/2.6 → 10.4/13.0 → **2.6/2.7** |
| MM_Run_Fwd | 45.2/39.5 → 5.2/11.4 → **2.6/2.7** |
| MM_Idle | 1.9/1.6 → 4.1/7.8 → **2.6/2.7** |

2.6/2.7이 바닥인 이유는 LAFAN 아래팔이 늘 약 2°(채널 평균 0.036) 비틀려 있는데 이동 후에는 0°가 되기 때문입니다. 비틀림을 LAFAN 평균(2°)까지만 옮기는 방식도 시험했지만 결과가 엇갈려(튐 프레임 16 → 17, 자기 복원 0.7% 개선) 단순한 쪽을 택했습니다. 손으로 옮긴 뒤 손의 z는 대부분 3 이하이고(최대 4.1, MF_Run), 넘치는 값은 클램프가 처리합니다.

### 3.5 목표 방향 — `endpoint_velocity` 배치

두 입력은 각자 9번 프레임의 골반 방향으로 정렬돼 있어서, 모델 진입점에서 정렬을 되돌려 시작 클립 좌표계로 옮긴 뒤 목표 위치를 정합니다(`place_target`). 기존 `endpoint_velocity`는 이때 목표 첫 프레임의 **골반 방향**을 시작 마지막 프레임의 골반 방향에 맞춰 돌렸습니다. "골반 방향 = 가야 할 방향"이라는 가정입니다.

A_Idle은 이 가정이 맞지 않습니다. 골반·다리·어깨·발끝이 모두 Walk·Jog의 진행 방향(UE +Y)에서 21~23° 돌아가 있습니다(UE 월드 기준 골반 110.9°, Walk 88.6°, Jog 이동 방향 90.0°). 그래서 기존 배치에서는 다음 문제가 생겼습니다. 이전 어댑터(Baseline)에도 똑같이 있던 문제입니다.

| 전환 | 끝 골반 방향 (원본 목표 클립 대비) | 끝 5프레임 이동 방향 (앞 = 90°) |
| --- | --- | --- |
| IdleToJog | +22.7° | 114° (대각선) |
| IdleToWalk | +22.8° | 119° |
| JogToIdle | −22.6° | — |
| WalkToIdle | −22.2° | — |
| WalkToJog · JogToWalk | 0.5° 이하 | 91° |

게임에서는 클립이 같은 컴포넌트 공간에서 이어 재생되므로, 전환이 끝난 뒤 원래 Jog 루프나 Idle을 틀면 그 순간 23°가 한 번에 튑니다.

이제 `endpoint_velocity`는 목표 클립을 **내보낸 방향 그대로** 둡니다. 위치는 이전처럼 시작 문맥의 마지막 3개 수평 이동량 평균과 목표→다음 이동량을 평균해 N+1 구간 앞에 놓습니다. 23° 회전은 모델이 생성 구간에서 만들고, 6개 전환 모두 끝 골반 방향이 원본과 0.0°로 일치합니다(IdleToJog 끝 이동 방향 90.5°). 시작·목표 클립의 root 본이 돌아 있지 않다고 가정합니다. Idle_Walk_Jog·MM 클립의 목표 프레임은 모두 이 조건을 만족합니다. 회전 루트 모션 클립의 중간 프레임을 목표로 쓰려면 내보내기에 root yaw를 함께 기록해야 합니다.

`continue_context`(이전 결과 재현용)와 `preserve_exported`는 바꾸지 않았습니다. 자기 복원 평가(4.2)는 `preserve_exported`를 쓰므로 영향이 없습니다.

### 3.7 안전장치와 기록

- 보정 파일에 기록된 보정 행렬 해시가 현재 `rest_pose_corrections_22_prototype.json`과 다르면 실행을 거부합니다. 보정 행렬을 바꾸면 롤을 다시 추정해야 합니다.
- 입력의 `mapping_source_sha256`에 다른 보정 행렬 해시가 있으면 실행을 거부합니다.
- Git의 `core.autocrlf` 설정에 따라 보정 행렬 JSON이 LF 또는 CRLF로 체크아웃되므로, 해시는 두 줄바꿈 형태와 모두 비교합니다. 보정 파일에는 LF 기준 해시를 기록합니다.
- 출력 `inference.frame_refinement`에 보정 파일 경로·해시·롤 값을, `inference.input_z_clamp`와 `diagnostics.input_z_clamp`에 클램프 설정과 실제로 잘린 값 개수, 클램프 전 최대 z를 남깁니다. `inference.twist_transfer`에 비틀림 이동 관절을, `diagnostics.twist_transfer_degrees`에 관절별 [시작, 목표] 비틀림 각도를 남깁니다.

### 3.8 시험했지만 넣지 않은 것

아래의 "현재 기준"은 목표 방향 수정(3.5) 전, 비틀림 이동까지 넣은 상태입니다.

| 방법 | 결과 (전환 6개 튐 프레임) | 판단 |
| --- | --- | --- |
| 접합부 속도 맞춤 후처리 (5차 다항식 감쇠) | 현재 기준 N=20 16 → 16~17, N=10 12 → 10~11, 자세 11~22° 변경 | 이득에 비해 자세 변경이 큼 |
| 선형 끝점 잔차 (루트 경계 보정의 회전판) | 1차 기준 N=20 29 → 20이지만 끝 접합부 가속 14.3 → 19.1 | 끝이 더 튐 |
| 강체 클램프 (문맥 전체에 같은 회전 차이) | 현재 기준 N=10·20·30 12·16·25 → 17·14·25 | 엇갈림 |
| 클램프 끔 | 현재 기준 N=20 16 → 48 | 나빠짐 |

공식 코드의 후처리(`anim_post_process`)는 생성 구간 전체에 시작·끝 차이의 평균인 상수 하나를 더합니다. 그래서 양 끝 차이가 다르면 절반씩 남고, 이것이 접합부 튐의 나머지 원인입니다. 다만 속도를 맞추는 후처리는 비틀림 이동 뒤에는 남은 튐을 거의 줄이지 못하면서 자세를 크게 바꿔서 넣지 않았습니다.

## 6. 한계와 다음 단계

- **Jump·Land·Fall**: 개선 후에도 모델이 단순 보간보다 나쁩니다(1.50배). LAFAN에 없는 Manny 키프레임 동작의 한계로 보입니다.
- **지면 관통**: 일부 전환에서 발끝이 지면 아래로 들어갑니다(Idle_Walk_Jog에서는 JogToIdle −3.5 cm, Manny Run 계열은 최대 −6.7 cm). 발 IK 후처리(접촉 검출 → 발 고정 → 2본 IK)가 필요합니다.
- **목표 직전 팔 감속**: Jog로 들어가는 전환에서 모델이 목표 직전 몇 프레임 동안 팔을 거의 멈췄다가 마지막 한 프레임에 따라붙는 현상이 줄었지만 남아 있습니다(WalkToJog 접합부 팔 가속 10.1°/프레임², 원본 Jog 최대 4.9). 공식 후처리가 상수 하나로 양 끝을 맞추는 구조의 한계이고, 속도 맞춤 후처리는 3.8과 같이 이득이 없었습니다.
- **전환 길이**: 공식 모델은 5~30프레임으로 학습됐습니다. 31~45는 외삽 구간이라 끝부분에서 감속 후 튀는 현상이 남습니다. N=30에서도 튐 프레임이 N=20보다 많습니다(26 대 15).
- **위상 선택**: 시작·목표 프레임 조합에 따라 발 미끄러짐이 최대 7배 달라집니다. 후보를 일괄 추론해 고르는 기능이 다음 과제입니다.
- **나머지 본**: 손가락·twist·IK 본은 아직 reference pose로 저장되어 경계에서 손 모양이 바뀔 수 있습니다.
- **뼈 방향**: 팔 프레임의 5~7° 방향 기울기는 롤 보정에 포함하지 않았습니다(클램프로 완화).
